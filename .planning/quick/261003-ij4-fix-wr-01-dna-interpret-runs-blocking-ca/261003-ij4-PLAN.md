<objective>
Close WR-01 from the Phase 05 incremental review (05-REVIEW.md:198-210, commit a943411): `_dna_interpret`
calls the synchronous captum attribution `interpreter.interpret(...)` directly on the event-loop thread
(dnallm/mcp/server.py:1565-1571). `asyncio.wait_for` in `_with_timeout_wrapper` (server.py:301) can only
fire at an await point, so while the single loop thread runs a long interpretation (observed 172s on a
non-mamba model against a 30s cap), the dna_interpret timeout wrapper is dead code and every client on
every transport is frozen — the same serving-liveness hazard class the mamba guard (server.py:1519-1539)
addresses for mamba models only.

Fix shape per the reviewer: run the blocking body through `loop.run_in_executor` like the predict paths
(the bridging pattern proven in ModelManager and just hardened by quick 261003-hhj / CR-01).

One deliberate addition beyond the bare executor move, decided at planning time: the closure acquires a
dedicated `threading.Lock` (`_interpret_thread_lock`) INSIDE the executor-submitted callable, mirroring
the CR-01-hardened predict paths. Reason: today the loop-thread execution implicitly serializes all
interpretations at one per process; a bare run_in_executor would silently drop that invariant, letting a
client timeout→retry loop stack unbounded orphaned captum backward passes on one shared torch model. The
lock caps concurrent interpretations at 1 across the cancellation boundary. It is deliberately NOT
`_infer_thread_lock`: DNAInterpret uses no DataLoader (verified: no DataLoader/infer_seqs references in
dnallm/inference/interpret.py — pure captum on tensors, no fork-unsafe window), and attributions must not
queue behind minutes-long predicts.

Known accepted property (same as CR-01): on timeout, only the await is cancelled — the underlying
executor thread keeps running to completion. The regression tests assert loop responsiveness and flight
retention, never thread cancellation.

Purpose: restore serving liveness for the whole MCP server during long interpretations and make the
30s tool timeout real for dna_interpret.

Output: dnallm/mcp/server.py fixed (executor offload + interpret single-flight lock),
tests/mcp/test_interpret_tool.py regression tests that are red on current code and green after the fix,
committed together per the owner rule that every dnallm/ change ships with pytest coverage in the same
change.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| MCP client → server tools | Untrusted request timing and load: a client can submit long attributions, let them hit tool_timeout_seconds (30s default), and immediately retry — deliberately or accidentally overlapping requests |
| event loop → default executor threads | asyncio cancellation crosses this boundary one-way: the coroutine dies, the thread does not (orphaned interpretation runs to completion) |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-quick-wr01-01 | Denial of Service | _dna_interpret inline captum work on the event-loop thread | high | mitigate | Task 2 moves the blocking block (instantiation + layer detection + interpret) into `run_in_executor(None, _run_interpretation)`; Task 1 Tests 1-2 pin the fix (health_check heartbeat completes during a blocked attribution; the 30s wrapper returns error_type "timeout" while the attribution is still in flight) |
