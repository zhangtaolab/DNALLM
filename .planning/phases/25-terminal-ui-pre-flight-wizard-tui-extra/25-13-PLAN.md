## Objective

Close the two layout defects the Phase-25 re-verification found, without touching the core, the copy layer, or any behaviour: the config error pane must lay out and expose every row it holds (CR-02), and the task-type hint must stop burying the panel's first control (WR-08).

This plan closes failed truths **31, 32, 36 and 43**. It does **not** close truth 44 (already verified — re-proven here as a gate), and it deliberately does **not** close the WR-09 advisory (the suitability "Use this model" action staying below the fold with a large report), IN-07, IN-08, IN-09 or IN-10 — all four are recorded as explicitly deferred below.

Purpose: 25-12 was green at the source level and red on the screen. The error pane is a fixed-height `Static` whose `overflow-y: auto` is inert in Textual 8, so the selector that gates "Save this config" silently dropped every row past the 14th; the same pane is the only place the eight-value task-type sentence is ever rendered, so the completeness claim was true only in the string, never on the display. The task-type hint is 453 characters and renders 15 rows between the label and the input in a 9-row form viewport, so the panel opened on a wall of vocabulary with its first control off-screen. Both defects are invisible to `.content` assertions, which is why the suite passed. This plan fixes the layouts and replaces the blind assertions with geometry that fails on the pre-fix tree.

Output: an error pane that lays out what it holds and scrolls with the side column, a form whose first control is inside the viewport at 80x24 in both the clean and the error state, and regression tests that measure the rendered geometry rather than the stored string.

## One plan, not two

GAP 1, GAP 2 and GAP 3 touch the same three files and the same 80x24 geometry. The hint fix changes how many rows `#config-form` has at 80x24, and the error-pane fix changes how tall `#config-side` must be; both are decided in one CSS block and both are proven in the same tests. Splitting them would serialise two plans on `dnallm/tui/app.py` and `tests/tui/test_screens.py` for no parallel gain, so this is **one plan with two tasks**: the tracer (error pane, GAP 1 + GAP 2) first, then the expansion (hint layout, GAP 3). Both scenarios are folded into Pilot runs that already exist, so this plan adds **no** `app.run_test` call; the `tests/tui` wall-time budget is re-adjudicated to <=50.0 s in "Locked in-plan decisions" so re-verification reads the measured baseline, not the outgrown <=45 s figure, as the contract.

## Locked in-plan decisions

- **The error pane gives up its cap; the side column carries the scroll.** `#config-errors` becomes `height: auto` with no `max-height` and no `overflow-y`. Chosen over wrapping the `Static` in its own `VerticalScroll` because at 80x24 the side viewport is only 8-10 rows: a capped 14-row inner scroll box would itself need scrolling, forcing the user to scroll twice for the one message that blocks saving. Measured on the running Pilot app at 80x24 with one bad `task_type`: the pane lays out 17 rows (25 with details), the side's scroll range reaches the last row, and the last row is reachable. At 100x40 the pane fits outright (13 rows in a 26-row side).
- **The test's oracle is Textual's own layout, not a re-implementation.** The strengthened test asserts `pane.region.height >= pane.visual.get_height(pane.styles, pane.region.width)`. `Content.get_height` is the exact function Textual uses to size a `Static`, so the assertion says "the widget lays out as many rows as its text needs" and cannot drift with a wrapping-algorithm change. Measured pre-fix: 14 laid out against 17 needed (details off) and 14 against 25 (details on); at 100x40 with several errors, 14 against 36. Post-fix: 17/17, 25/25, 36/36. A `textwrap`-based row count was measured and rejected: it disagrees with Textual by one row when a raw Pydantic message carries an unbreakable regex token.
- **Asserting `.content` alone is not enough; geometry alone is not enough either.** Scrolling the side brings even the *capped* pane's last laid-out row into view (measured `tail_visible=True` on the pre-fix tree), so a reachability assertion by itself would not have caught CR-02. The test pairs three checks: the laid-out height against the height the content needs, the last laid-out row's *text* against the tail sentence, and reachability of that row after a real scroll.
- **Every field hint moves below its input.** One rule in `compose`, applied to all twelve hinted fields, rather than a special case for `task_type`: help text under a control is the standard reading order, and a single hint rendered in a different position from the other eleven reads as a bug. No copy string changes, so the four-site completeness contract is untouched — this is the "preserve" branch of GAP 3's either/or, not the renegotiate branch.
- **Two rows are reclaimed so the invariant holds in the error state too.** `#config-section-task { margin-top: 0; }` removes the gap between the status line and the first section, and `#config-output-row` drops from `margin: 1 2` to `margin: 0 2`. Measured at 80x24: the form viewport goes from 9 rows to 11, the task-type input from y=23 to y=7 (contained), and with a validation error showing (status wraps to 4 rows, form 10 rows) the input at y=8 is still contained. Without both changes the input is exactly on the edge in the clean state and one row out in the error state; an invariant that only holds while nothing is wrong is not the invariant WR-08 asks for.
- **The completeness contract is preserved, explicitly.** No edit to `dnallm/tui/copy.py`, `tests/tui/test_copy.py`, `dnallm/tui/screens/suitability.py`, or any core file. GAP 2's "prove it where it is shown" is delivered by the render-site assertion (the last laid-out row carries `binary_classification`), not by shortening or splitting the sentence.
- **The WR-08 hint stays 453 characters and keeps all eight glosses.** Shortening the hint to values-only (the review's suggestion) does not fix the defect on its own: seven rows already sit above the hint at 80x24 (title 1 + status 3 + section margin 1 + heading 1 + label 1, measured), so a one-line hint rendering three rows at 32 columns puts the input at y=11 — still outside the 9-row viewport. The rows above the input, not the hint's length, are what bury it.
- **The tests/tui wall-time budget is re-adjudicated to <=50.0 s, and the new scenarios are folded into existing Pilot runs.** Baseline measured at revision time (2026-10-21, unmodified tree): `pytest tests/tui -q` = 199 passed in 45.00 s, 45.65 s and 46.03 s across three runs — the lane is already at or above the old <=45 s ceiling before this plan adds anything, so the <=45 s figure no longer describes the tree and cannot be the gate. The re-adjudicated ceiling is **<=50.0 s** (about 9% headroom over the fastest baseline for machine variance), with the per-test <=60 s budget and the 300 s pytest timeout unchanged. Both new scenarios ride existing app runs instead of adding two: the 100x40 several-error leg runs after `await pilot.resize_terminal(100, 40)` and a second `ConfigScreen` push inside the strengthened 80x24 error test — measured 0.296 s for resize + push + settle + details press, versus 0.40–0.60 s for a fresh `app.run_test` — and the first-field/adjacency assertions are appended to the existing clean-state `test_the_hinted_form_stays_legible_at_80x24`, adding no app run at all. Expected lane after this plan: ~46 s, inside the new ceiling.
- **Deferred, not fixed here (rationale recorded):** WR-09 (the suitability use action below the fold with a realistic report — 25-12's contract accepts scroll-to-reach, and pinning the action row would change the suitability panel's tested behaviour); IN-07 (details toggle enabled for pass-through errors — cosmetic, and the toggle's truth is about mapped errors); IN-08 (`not_a_number` example — copy wording, outside the layout gap); IN-09 (`TASK_TYPE_GLOSSES` mutable — copy-layer hardening, and this plan must not touch `copy.py`); IN-10 (`benchmark.benchmark.name` — copy-layer label bug). Also deferred: the `#config-preview { max-height: 24 }` cap is the same class of inert overflow, but it is not a failed truth and a generated config preview measures 17 rows at 80x24 — it needs its own measurement and test, so it stays out of this gap closure's blast radius.
