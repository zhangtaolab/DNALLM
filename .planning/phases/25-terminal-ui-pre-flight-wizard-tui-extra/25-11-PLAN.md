## Objective

Close the two copy-layer gaps the phase's own UAT found (D-10), without touching the core or any behaviour: the config error pane must explain each validation problem in words a biologist can act on while keeping the core's exact message available on demand, and every config label, heading and hint that carries an ML term must carry a one-line plain-language gloss — with the underlying config keys and values still shown verbatim.

Purpose: TUI-06 delivered the config panel's mechanics but not its readability; a user who cannot understand "String should match pattern '^(embedding|mask|...'" or "Weight decay" cannot self-correct, which defeats SC3's "leave with a validated config".

Output: a pure error-message mapper and gloss table in `dnallm/tui/copy.py`, the matching rendering in `ConfigScreen` (a details control and per-field hints), and tests that pin the exact sentences at 80x24.

## Locked in-plan decisions

- **The mapper keys on `(section, section-relative field, kind)`, not on free text.** `SectionError` exposes only `section`, `field` and `message` (verified: `dnallm/preflight/report.py:365-378`), so the kind is classified from a fixed, ordered fragment table covering the core's reason-code prefixes and the Pydantic message families this panel can produce. The core emits two field conventions for the same concept: Pydantic-derived errors carry the dotted path (`task.task_type`, `finetune.learning_rate` — `_validation_errors` at `dnallm/preflight/config_gen.py:101-124`) while its hand-built semantic errors carry the bare name (`task_type`, `model`, `sections` — `config_gen.py:149-153`, `:282-322`, `:399-404`). The lookup normalises both to one key (strip a leading `"<section>."`), so a table entry cannot silently miss a real error and a future hand-built `SectionError` cannot leak raw text. A core change to add a reason field is out of scope (Phase 23 owns validation) and unnecessary.
- **Exact entry, then generic template, then the core's own text.** A missing exact entry falls back to a per-kind generic sentence using the field's friendly label (or the field path when none exists); a missing kind falls back to the raw message unchanged. No branch invents a message that misdescribes the problem.
- **Raw detail is on demand, never silently dropped.** A `#config-error-details` button toggles a second line per mapped error; a detail line is emitted only when the plain sentence differs from the core's message, so nothing is duplicated.
- **Labels are prose, keys are identifiers.** Labels and hints may be rewritten freely; the preview stays `render_yaml(raw)`, so `num_train_epochs`, `lora_alpha` and friends remain byte-verbatim (D-10).
- **Hints sit under the label and above the input**, rendered literally (`markup=False`) from `CONFIG_FIELD_HINTS`; a field with no hint renders none.
- **No behaviour change:** the save gate, the kept-as-is block, the read-only facts and the seam table are untouched.
