## Summary

The phase adds a shared plain-language support vocabulary (`dnallm/models/support.py`) wired into the docs generator, the TUI suitability listing, and the MCP registry listing; four census-measured transformers-5 repairs (ROPE `default`, GENA-LM `token_type_ids`, MutBERT forward, DNABERT-2 pre-construction shims); upgraded GPN/Omni-DNA ImportError guidance; the CrossDNA checkpoint-route census alignment; and the committed census write-back plus regenerated docs. The committed data is internally consistent (artifact ↔ registry ↔ docs gates cross-check cleanly; counts 19/21/5/4/0 over 49 pretrained entries), the compat rungs are absence-gated, probe-gated, and sentinel-idempotent as their contract requires, and the census/write-back fail-closed posture is mostly genuine.

The one Critical finding is a hole in that fail-closed posture: `compat_verdict` maps an `import-fail` **non-representative** record with no skip disposition to `import-verified-tf5` — a false "family-tested" verdict for a model whose import demonstrably failed (reproduced live against the shipped script). The independent mirror in `tests/models/test_model_info_registry.py` shares the same else-branch, so neither the tool nor the gate would catch it; today's committed artifact is saved only because every failure record happens to carry a hand-authored disposition. Warnings cover probe-subprocess credential passthrough beyond the CI prefixes, a README dependency-table gap for two of the eight remediated models, a positional-argument contract narrowing in the MutBERT wrapper, and spoofable child-verdict parsing in the census probes.

## Narrative Findings (AI reviewer)

### CR-01: `compat_verdict` returns a false `import-verified-tf5` for an import-failed non-representative record

**File:** `scripts/census_compat.py:1527-1533`
**Issue:** The mapping function's non-representative fallback never checks the record's own status. For a record with `status="import-fail"`, no skip disposition, and no green load, control falls through the skip arm (no disposition), the fix arm (needs a green load), and the green-load arm, and lands on:

```python
if not record.get("is_family_rep"):
    representative = family_reps.get(record.get("family"))
    if representative:
        return ("import-verified-tf5", f"{stamp}; load inferred from family representative {representative}")
```

Reproduced live by loading the shipped script and calling `compat_verdict` with a well-formed `import-fail` non-rep record of family `EsmForMaskedLM`:

```
('import-verified-tf5', 'ms org/new-sibling@abc123; load inferred from family representative zhangtaolab/plant-nucleotide-transformer-BPE')
```

Consequences: (1) `--write-registry --apply` on a fresh artifact writes a false "Tested loading its code; full run inferred…" / `family-tested` verdict into the shipped registry whenever a non-representative entry newly fails its import and no disposition has been authored yet; (2) `--verify` computes the same false expectation, so if the stale committed status was already `import-verified-tf5` the whole composed lane stays green and masks the regression entirely. This violates the function's own documented fail-closed contract ("an unclassifiable shape must never silently pass") and its mapping-table wording ("a non-representative **import/arch-ok** entry maps to import-verified-tf5" — the status is never verified). The independent re-implementation in `tests/models/test_model_info_registry.py:523` (`else: expected = "import-verified-tf5"`) shares the flaw, so it cannot catch the drift. Today's committed artifact is safe only because `TestDispositionCompleteness` forces dispositions onto every failure record before commit — a backstop that lives outside the tool.
**Fix:** Gate the inference branch on the record's own import status, and fail closed otherwise:

```python
if (
    not record.get("is_family_rep")
    and status in ("import-ok", "arch-ok")
):
    representative = family_reps.get(record.get("family"))
    if representative:
        return ("import-verified-tf5", ...)
raise ValueError(
    f"census record for {repo} (status {status!r}) carries no green load and "
    "no skip disposition - cannot map it to a registry status"
)
```

Mirror the same status guard into `test_compat_census_artifact_matches_registry` in `tests/models/test_model_info_registry.py` so the independent gate cannot self-approve the same false verdict.

## Warnings

### WR-01: Probe subprocesses inherit hub credentials beyond the sanitized CI prefixes

**File:** `scripts/census_compat.py:82` (and `sanitized_probe_env`, lines 686-703)
**Issue:** `BLOCKED_PROBE_ENV_PREFIXES = ("GITHUB_", "RUNNER_", "ACTIONS_")` strips CI credentials, but the probe/load children execute arbitrary untrusted `trust_remote_code` and still inherit every other secret in the parent environment — notably `HF_TOKEN` / `HF_TOKEN_PATH` (present on the nightly runner and any authenticated dev box), plus any other `*_TOKEN`-style credentials. The census only reads public repos through the mirror, so the token is not needed by the child; handing it to untrusted code is a pure credential-exposure risk inside the phase's own stated threat model (WR-03: "they must never see runner credentials or CI state").
**Fix:** Extend the blocked set with `("HF_TOKEN", "HF_TOKEN_PATH", "HUGGING_FACE_HUB_TOKEN")` (or strip every `*_TOKEN`/`*_KEY` variable not on an explicit allowlist) in `sanitized_probe_env`, and pin the added names in `TestProbeEnvSanitization`.

### WR-02: README special-model dependency table omits GENA-LM-BigBird and CrossDNA

**File:** `README.md:265-281`
**Issue:** The section states "Several models require extra dependencies to train or inference. These models are listed below:", but the table omits two of the eight models this phase documents as needing external packages: GENA-LM-BigBird (`deepspeed`) and CrossDNA (separately compiled `flash-attn`), both present in `docs/user_guide/optional_dependencies.md` ("The eight at a glance") and both named in the README's own "Specialized Models" feature bullet without any dependency flag. A README-only reader gets an incomplete dependency list for exactly the models the compatibility campaign flagged.
**Fix:** Add rows for GENA-LM-BigBird (`deepspeed`, link `optional_dependencies.md`) and CrossDNA (`flash-attn`, link `optional_dependencies.md`) to the table.

### WR-03: MutBERT guarded forward narrows the wrapped forward's positional call contract

**File:** `dnallm/utils/transformers_compat.py:2055-2069`
**Issue:** `_guarded_mutbert_forward(input_ids=None, *, _original=..., _module=..., **kwargs)` accepts only `input_ids` positionally and forces everything else keyword-only, then delegates as `_original(input_ids=input_ids, **kwargs)`. The remote `RoPEBertModel.forward` it replaces is a normal `(self, input_ids=None, attention_mask=None, ...)` signature, so any caller that passed a second positional argument (`module(input_ids, attention_mask)` — valid before the wrap) now raises `TypeError: ... takes 1 positional argument`. The census probe calls `model(input_ids)`, so the measured evidence is green, but the wrapper silently changes the module's public call contract for every other caller.
**Fix:** Preserve positional arity in the wrapper, e.g. `def _guarded_mutbert_forward(input_ids=None, *pos_args, _original=..., _module=..., **kwargs)` and delegate with `_original(input_ids, *pos_args, **kwargs)` (routing to `inputs_embeds` only when `input_ids` is a 2-D tensor and no `inputs_embeds`/positional extras are present).

### WR-04: Census verdict parsing trusts child stdout; untrusted remote code can forge a green verdict

**File:** `scripts/census_compat.py:730-746` (and the same scan in `run_load_probe`, lines 1148-1165)
**Issue:** `run_import_probe` / `run_load_probe` take the LAST stdout line that starts with `{` and contains `"ok"` as the child's verdict. The child executes arbitrary third-party code; that code can print a forged `{"ok": true, ...}` line after the program's own final `print` (e.g., from an `atexit` hook, or simply by not raising and printing last), turning a failed import/load into recorded green evidence. This evidence is what `--write-registry --apply` and the docs generator turn into user-facing "works" claims, so a model author has a direct incentive to spoof it. The current `subprocess.run(capture_output=True)` parsing provides no integrity boundary.
**Fix:** Wrap the program's verdict in an unambiguous frame the remote code cannot trivially produce as the final line — e.g., print the JSON payload followed by a fixed sentinel line and parse only the line immediately preceding the sentinel, or have the child write the verdict to a path passed via a per-run temp file (argv, not env) and parse that file, ignoring stdout entirely for verdicts.

**File:** `tests/models/test_census_compat.py:340-345`
**Issue:** The comment on `test_real_layout_preference_does_not_win_without_config` asserts "The real repo: 8.1M is the handler's preferred dir but carries no config.json; the unique-valid-child rule selects 519M instead." The committed registry evidence (`dnallm/models/model_info.yaml:485`, "handler-preferred 8.1M checkpoint") and `docs/user_guide/optional_dependencies.md` (CrossDNA section: the census "resolve[s] the same checkpoint subdirectory (8.1M...)") both say the real repo resolves to 8.1M — which the resolver only picks when 8.1M carries a readable config. The synthetic fixture is fine; the "real repo" claim in the comment is wrong and will mislead the next maintainer.
**Fix:** Reword the comment to describe the fixture: "Synthetic variant of the repo layout: the preferred 8.1M dir without a config.json cannot win; the unique-valid-child rule selects 519M (on the real repo 8.1M carries a config, so the preferred-dir rule wins)."

### IN-02: `_QuantStatProxy` does not forward dunder-protocol operations

**File:** `dnallm/utils/transformers_compat.py:296-314`
**Issue:** The proxy's docstring promises it "forwards every attribute access", but `__getattr__` only covers attribute lookups. Data-model operations are resolved on the type, so `len(proxy)`, `proxy[0]`, iteration, and calling the proxy raise `TypeError` instead of delegating to the wrapped tensor. Any read-only consumer that subscripts or iterates the returned value breaks. (Pre-existing rung, in a file in scope.)
**Fix:** If a consumer ever needs it, add `__len__`, `__getitem__`, `__iter__`, and `__call__` pass-throughs to `_QuantStatProxy`; at minimum soften the docstring to "forwards attribute reads".

### IN-03: DNABERT-2 handler logger is named after the wrong module

**File:** `dnallm/models/special/dnabert2.py:9`
**Issue:** `logger = get_logger("dnallm.models.model")` attributes the handler's log records (including the "Triton version does not support, flash_attn_triton disabled." warning at line 252) to `dnallm.models.model`, defeating per-module log filtering.
**Fix:** `logger = get_logger("dnallm.models.special.dnabert2")`.

### IN-04: Redundant double `.lower()` in the DNABERT-2 path guard

**File:** `dnallm/models/special/dnabert2.py:223-227`
**Issue:** The guard computes `os.path.basename(model_path.lower())` for the first clause and `os.path.basename(model_path).lower()` for the second — two different spellings of the same normalization; both are case-insensitive, so the mixed form is pure drift bait.
**Fix:** Compute `basename = os.path.basename(model_path).lower()` once and test `"dnabert-2" not in basename and "dnabert-s" not in basename`.

### IN-05: Triton-disable path mutates the shared snapshot cache with a crash/race window

**File:** `dnallm/models/special/dnabert2.py:239-265`
**Issue:** The legacy workaround overwrites `flash_attn_triton.py` inside the fetched snapshot directory (HF-hub snapshots are symlinks into a shared blob store, and the write follows the symlink) and restores it in a `finally`. If the process dies between disable and restore, the cache is left with the "Temporarily disabled" stub; if two threads load the same checkpoint concurrently (MCP `ModelManager` loads in executor threads), the disable/restore windows race. The new in-memory `_neutralize_dnabert2_triton` reaches the same fallback without touching the cache; the file path is retained for the legacy flow.
**Fix:** Prefer the in-memory neutralization whenever it applies and keep the file overwrite only as a last resort (or write a sibling copy and point `sys.path` at it), and hold a module-level lock around the disable/restore window.

### IN-06: Two config keys resolving to the same registry entry silently collapse in the MCP overlay

**File:** `dnallm/mcp/server.py:834-847`
**Issue:** The overlay is keyed by `registry_entry.name`: `overlay[registry_entry.name] = {"server_config_key": key, ...}`. Two server-config keys that resolve to the same registry entry (an easy misconfiguration) silently overwrite each other — only the later key's `server_config_key`/`enabled` survives, `configured_count` undercounts, and the dropped key never appears in `unmatched_configured`, so the listing reports no anomaly.
**Fix:** Detect the collision and surface it (e.g., append the duplicate key to `unmatched_configured` under a clear label, or make the overlay value carry a list of config keys).

### IN-07: The `needs pip install gpn` support word promises more than the measured wheel delivers

**File:** `dnallm/models/support.py:52-56` (pinned by `tests/models/test_support.py`, `tests/mcp/test_server_streaming.py`)
**Issue:** The exact phrase shown in the docs/TUI/MCP listings for `songlab/gpn-brassicales` is "needs pip install gpn", but the repository's own measured guidance (`dnallm/models/special/gpn.py:24-33`, `docs/user_guide/optional_dependencies.md` GPN section) records that the published `gpn` 0.9.0 wheel does not provide the `gpn.model` module the handler imports — the documented working route is a source install in a separate Python 3.13 environment. A user who follows just the listing word will still hit the ImportError. The phrase is owner-pinned (D-10/D-11), so this is recorded as an accuracy tension rather than a code change.
**Fix:** If the vocabulary can be revisited, use a phrase that does not imply sufficiency (e.g., "needs the gpn package — see the support guide"); otherwise leave as pinned and rely on the guide link beside the word.

### IN-08: `test_extra_extends_the_registry` permanently mutates the module-level GPN name list

**File:** `tests/models/test_special/test_family_handlers.py:71-79`
**Issue:** The test calls `_handle_gpn_models("my-custom-gpn", extra="my-custom-gpn")`, which appends to the real module-level `gpn_models` list with no monkeypatch isolation — the entry persists for the rest of the session, so any later call resolving a name containing `my-custom-gpn` hits the GPN ImportError gate unexpectedly. `TestHandlerExtraRegistration` (lines 838-875) does isolate correctly by copying the list first; this test is the odd one out. (The underlying `extra`-appends-to-module-global pattern shared by all family handlers is itself permanent, unbounded state mutation, but it matches the repo-wide handler convention.)
**Fix:** Copy the list before mutating, as the sibling tests do:

```python
import dnallm.models.special.gpn as gpn_module
registry = list(gpn_module.gpn_models)
monkeypatch.setattr(gpn_module, "gpn_models", registry)
```
