# Quick Task 261011-0a3: numpy loj-intersect parity spike vs bedtools Summary

Evidence-only spike proving a zero-dependency numpy left-outer-join interval intersect matches `bedtools intersect -loj` v2.31.1 row-for-row, order-for-order and null-for-null — VERDICT: PARITY across 2000 seeded randomized NER-shaped cases and 11 handcrafted edge cases with zero mismatches on BOTH gates — so windows-ledger id 19's NER half of the platform split (Linux keeps pybedtools, Windows gets the numpy equivalent) is evidence-backed for v1.3.

## What Was Built

`spike_loj_parity.py` (1523 lines, task artifact — never library code), stdlib + numpy only. Algorithm sketch:

1. `parse_bed` — BED3+ rows (arbitrary trailing columns preserved verbatim), integer coords with `0 <= start < end`, file order preserved and NEVER sorted, grouped later by exact chromosome-string key (`Chr1` != `chr1`); loud `ValueError` naming file + line on malformed rows.
2. `loj_intersect_np` — the join: every A row survives in A-file order; per A row, same-chrom B rows with a half-open overlap (`b.start < a.end AND a.start < b.end` — touching boundaries do NOT overlap) emit one line per pair in B-file order via numpy broadcasting (`mask = (b_starts < a_end) & (b_ends > a_start)`, `np.nonzero` in B-file order); no-hit rows emit once with the B side null-filled from the pinned map. A JOIN — nothing merged, nothing coalesced; duplicates on either side multiply per copy.
3. `_null_b_fields` — the oracle-pinned null-B vector as a function of B column count (and, at count 5, score-column int-parseability); empty B file defaults to the 3-column form bedtools emits.
4. `run_bedtools_loj` — fixed argv `[bin, "intersect", "-a", a, "-b", b, "-loj"]` (+ `-sorted` variant for the sort-requirement pin), `text=True, capture_output=True, check=True`, never shell; plus `resolve_bedtools` (shutil.which + `--version` echo + `--bedtools` override so a shadowed PATH binary is detectable).
5. Four empirical pin probes + 11 handcrafted edge cases + seeded randomized corpus, all comparing numpy against the live oracle on both gates (canonical row-set-with-multiplicity; exact line sequence), with `failures/case_<label>/` reproduction dirs (a.bed, b.bed, oracle_output.txt, numpy_output.txt) on any mismatch.

Numpy-only rationale: the join arithmetic runs on per-chromosome int64 start/end arrays and every additional BED column is a string payload carried along by row index, so pandas would add import weight with no arithmetic to do (same rationale as the wx2 jaccard spike). CLI: `--cases` (default 2000; 0 = pins + handcrafted only), `--seed` (default 20261011), `--bedtools`. Exit 0 iff VERDICT: PARITY.

## The Three Empirical Pins (verbatim from report.txt)

### Pin 1 — null-B fill per B column count (incl. column-count and content dependence)

```text
pin null-B fill (live oracle, no-hit A rows, per B column variant):
  B columns 3: literals ['.', '-1', '-1'] numpy-emit PASS
  B columns 4: literals ['.', '-1', '-1', '.'] numpy-emit PASS
  B columns 5 score col '0': literals ['.', '-1', '-1', '.', '-1'] numpy-emit PASS
  B columns 5 score col 'exon': literals ['.', '-1', '-1', '.', '.'] numpy-emit PASS
  B columns 6 score col 'exon': literals ['.', '-1', '-1', '.', '-1', '.'] numpy-emit PASS
  B columns 6 score col '0': literals ['.', '-1', '-1', '.', '-1', '.'] numpy-emit PASS
  B columns 7 score col '0': literals ['.', '-1', '-1', '.', '.', '.', '.'] numpy-emit PASS
  B columns 7 score col 'exon': literals ['.', '-1', '-1', '.', '.', '.', '.'] numpy-emit PASS
  empty B file: ['.', '-1', '-1'] (column count unknowable — oracle emits the 3-column null form) numpy-emit PASS
  pinned per-column-type map: chrom-col '.' | start-col '-1' | end-col '-1' | name-col/B4 '.' | score-col/B5 '-1' or '.' (content-dependent at count 5 only) | strand-and-beyond '.'
  pinned content rule: B count 5 score slot is '-1' iff column 5 parses as int, else '.'; B count 6 is ALWAYS '-1' and B count >= 7 ALWAYS '.' (both verified with numeric and non-numeric content) — the NER 6-column surface is content-independent
  NER shape (6-col B): iv.fields[10] == B column 5 == '-1' -> the consumer's `name == '-1'` intergenic branch FIRES under the pinned encoding
```

The decisive detail: the NER annotation B is 6 columns, so a no-hit A row carries B-side `.` `-1` `-1` `.` `-1` `.` — the BED "score" slot (B column 5 = `iv.fields[10]` in the consumer) is `-1`, NOT `.`. The consumer's `name == "-1"` intergenic branch therefore FIRES as written; a port that guessed all-trailing-`.` would silently fall through to the `zero_map.get(".0") -> None -> ne["intergenic"]` fallback and still label intergenic, but by accident rather than by the branch the code was written around.

### Pin 2 — plain -loj output order (incl. unsorted A)

```text
pin output order (unsorted A across 2 chroms, multi-hit rows, sorted B):
  gate numpy-sequence vs plain -loj raw: PASS (5 A rows, 9 output lines)
  -sorted variant on sorted copies: sequence DIFFERS from plain -loj (same 9 lines, same multiset)
  gate numpy-sequence vs -sorted oracle on sorted copies: PASS
  pinned rule: plain -loj emits output lines in A-file order; per A row the B hits appear in B-file order (verified on this probe: unsorted A, B-file order == start order here; unsorted-B order is exercised by the corpus)
```

The corpus settled the unsorted-B half the probe could not (its B was sorted): all 500 shuffled cases — both sides permuted — passed the exact-sequence gate against numpy's B-file-order emission, so B hits come out in B-file order even when B is unsorted.

### Pin 3 — sorted-input requirement (plain vs -sorted)

```text
pin sorted-input requirement (observed, gated on nothing per plan):
  plain -loj on unsorted input: ACCEPTED (exit 0)
  -loj -sorted on unsorted input: REJECTED (first stderr: ERROR: chromomsome sort ordering for file <tmpdir>/pinsort_a.bed is inconsistent with other files. Record was:)
  -loj -sorted on sorted copies: ACCEPTED (exit 0)
  finding: plain -loj needs no sorted input (the NER consumer's unsorted tokens_bed is legal); -sorted demands sorted input
```

## Implications for Windows-Ledger id 19 (NER port notes)

The NER half of the platform split **ships on this evidence**: jaccard parity did not transfer by assumption — loj is a join with its own null encoding, multiplicity and emission-order contracts — and all three are now oracle-pinned and reproduced exactly (2011 compared cases, 0 mismatches, both gates). What the Windows port of `tokens_to_nerdata` (generate_bpe_dataset.py + data_generation_and_inference.ipynb cell 8) must reproduce: (1) **Null encoding** — a no-hit A row against the 6-column annotation B carries B-side `.` `-1` `-1` `.` `-1` `.`; the port MUST emit `-1` in B column 5 because the consumer branches on `name == "-1"` where `name = iv.fields[10]` — that branch is live under the pinned encoding (a `.` there would push intergenic tokens through the accidental `zero_map`-fallback path instead). If the port ever feeds a non-6-column annotation, the null vector changes shape (count-5 score slot is content-dependent; >= 7 always `.`) — the production port should assert the 6-column shape or port `_null_b_fields` whole. (2) **Ordering guarantee** — plain `-loj` emits in A-file order with per-A B hits in B-file order, and accepts unsorted A and B; the consumer's ascending-coordinate traversal therefore works only because tokens_bed itself is near-sorted in practice (per-gene iteration), NOT because bedtools sorts — the port must likewise preserve input order (never sort) and must NOT assume hits arrive coordinate-sorted when B's file order differs from start order. (3) **Join, not merge** — one output line per A x B overlap pair, duplicate rows on either side multiplied per copy (the corpus's duplicates pattern pinned this on both sides); the consumer's `token_seen[gene]` dedup of `(start, end)` pairs already absorbs A-side duplication, so the port must keep emitting duplicates, not deduplicate early. (4) **Acceptance gate** — exon_f1=0.7522 in-band on BOTH paths remains the v1.3 gate this evidence enables: Windows CI (test-windows) becomes the numpy-path executor, and the dual-path check needs the same frozen Anno metric band, with v1.3 pinning the frozen-value comparison tolerance for trailing float deltas as already directed in the ledger entry.
