## D2 Verdict (the flagged human-judgment item)

**"Is the six-column table legible at 80x24?" — No, and it is not fully legible at 120x40 either.**

Measured with the real registry listing (236 rows) rendered headlessly:

- Table virtual content width is **~170 columns**. Visible table region: **74 chars at 80x24, 114 chars at 120x40**. The rendered 120x40 screen shows headers only through "Trained outputs" (whose own content is truncated to `no trained outpu`); **Availability and Support headers and cells are entirely off-screen to the right** and reachable only via the DataTable's horizontal scrollbar.
- At **80x24 the listing table's region starts at y=30** — below the 24-row viewport entirely. The user must scroll the page down and then scroll the table right to read any support word.
- Worst-case support words are the widest cells in the table: `not working with transformers 5` (30 chars, x1), `needs pip install ai2-olmo` (26, x1), `works with built-in fixes` (25, x14). The most common words are short (`family-tested` x122, `works` x82), so the overflow is driven by a handful of rows.
- Fairness note: horizontal overflow is **pre-existing** (the five-column table was already ~138 chars wide vs a 74–114 char viewport); this phase worsened it by ~32 chars (~23%). The regression is real but incremental, hence WARNING not BLOCKER — the phase's own claim "no new visual surface" is technically true, yet the pillar-2 effect of the addition is negative.

---

## Top 3 Priority Fixes

1. **Support (and Availability) columns invisible without horizontal scrolling at common terminal widths** — a biologist at 120 columns cannot see the support status the whole phase was built to surface without discovering the table's horizontal scroll — cap column widths (e.g., `TableColumn` fixed/auto-max) and abbreviate the long words (`not working with transformers 5` → `broken on transformers 5` or `needs: transformers 4`), or move Support ahead of the wide "Trained outputs"/"Availability" columns since it is the decision-critical fact.
2. **Listing below the fold at 80x24** — the declared minimum terminal size shows none of the listing (table starts at row 30 of 24) — scroll the page to the listing once the report lands (`screen.scroll_to_widget`), or collapse the task-type glossary that occupies the first 30 rows.
3. **Negative support statuses carry no visual signal** — `works` and `not working with transformers 5` render in identical plain text, so a scanning user can pick a broken model — prefix a plain glyph (`!` / `+`) or a Textual style on the support cell (staying inside the shared vocabulary; the word itself stays verbatim).

## Detailed Findings

### Pillar 1: Copywriting (4/4)
- `dnallm/models/support.py`: single shared source (`SUPPORT_WORDS`, `SUPPORT_WORD_BY_REPO`); no raw `tf_compat_status` enum reaches any listing (verified: TUI renders `entry.support` at `dnallm/tui/screens/suitability.py:364`; MCP calls `support_word(entry)` at `dnallm/mcp/server.py:862`).
- Vocabulary is plain-language per the biologist directive: "works", "family-tested", "works with built-in fixes", "needs pip install gpn", "untested". Honest degradation (`untested` for unresolvable/cyclic inheritance) instead of errors.
- Generic-label grep clean; the honest "never as-is" wording discipline (D-03) is respected — repaired models say "works with built-in fixes".

### Pillar 2: Visuals (2/4)
- `dnallm/tui/copy.py:309-316`: six columns, Support last. Structure is correct and index-safe (`_AVAILABILITY_COLUMN = 4` unchanged, `suitability.py:82`), but the rendered result overflows: measured table width ~170 vs viewports 74/114 (see D2 above). "Trained outputs" content truncated mid-word at 120x40.
- Empty "Models you asked about" verdict table renders header-only with no guidance row (pre-existing, out of this phase's diff but visible in capture).

### Pillar 3: Color (3/4)
- No hardcoded colors introduced; support cells are markup-free `Text` (`_cell(entry.support)`), consistent with the screen's no-markup contract.
- WARNING: no semantic differentiation between positive and negative support words (see fix 3). The Phase 26-02 callability ladder in MCP gets ordering; the TUI support word gets nothing.

### Pillar 4: Typography (4/4)
- One consistent cell style across all six columns; no per-surface font/weight drift possible (Textual DataTable, markup-free cells). Nothing added that diverges.

### Pillar 5: Spacing (3/4)
- No arbitrary spacing values; DataTable default padding only. The spacing problem is column-width allocation: six columns' content widths sum to ~170 chars with no width budgeting against the viewport. Not a violation of a scale (none declared), but a real layout gap.

### Pillar 6: Experience Design (3/4)
- Loading state: `probing…` placeholder preserved; refresh writer `_refresh_availability_cells` (`suitability.py:405-414`) writes only Coordinate column 4 — proven by `test_availability_updates_leave_the_support_cell_untouched`.
- On-demand probe and error paths unchanged and tested; cross-surface equality pinned (236 rows, all three surfaces).
- Deduction: the addition trades legibility for information density without any width-adaptive behavior; user task "see support status before choosing a model" now requires two scroll actions at common widths.
